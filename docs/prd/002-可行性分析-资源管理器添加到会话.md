# 可行性分析：资源管理器右键「添加到会话」功能

## 一、结论：可以实现，但需 3 处上游 custom_change

| 维度 | 评估 |
|---|---|
| **技术可行性** | ✅ 可以实现 |
| **上游文件改动** | **3 处** `custom_change`（比之前功能多） |
| **custom/ 新增** | 2 个 Action 类 + XML 注册 |
| **核心阻碍** | `PromptPanel.addAttachment()` 是 private，需逐层暴露 |
| **风险** | 中等 — 新会话创建后立即附加文件有时序问题 |

## 三、核心 API 链路（已验证）

### 3.1 文件引用的内部机制

```
用户在聊天框拖入/@引用文件
  → PromptPanel.addAttachment(PromptAttachment)  [private]
  → attachments 列表追加
  → 发送时 promptDto() 将附件转为 PromptPartDto
  → 后端收到 file 类型 part，动态读取文件内容

### 3.3 阻碍点：addAttachment 是 private

```
custom/ Action
  → SessionManager.addFileAttachments()  ← 需新增（custom_change）
    → SessionUi.addFileAttachments()     ← 需新增（custom_change）

**必须打开 3 层 private/internal 限制才能从 custom/ 调用。**

## 五、实现难点与风险

### 难点 1：新会话创建时序

`SessionSidePanelManager.newSession()` 创建新的 `SessionUi`，但新 UI 可能尚未完全初始化。
如果立即调用 `addFileAttachments()`，`current?.prompt` 可能为 null。

**解决**：在 `SessionSidePanelManager` 的 `addFileAttachments` 实现中使用 `ApplicationManager.invokeLater` 延迟附加。

### 难点 2：目录递归扫描不能阻塞 EDT

选中目录后递归扫描可能涉及大量文件 I/O。

**解决**：用 `ApplicationManager.executeOnPooledThread` 执行扫描，完成后回到 EDT 附加文件。

### 难点 3：PromptAttachment 构造

`PromptAttachmentExtractor.files()` 接受 `List<java.io.File>`，但我们从 Project View 拿到的是 `VirtualFile`。
需要将 `VirtualFile` 转为 `java.io.File`（`vFile.toNioPath().toFile()`）。

**解决**：在 Action 中完成转换。

### 难点 4：3 处上游改动增加合并维护成本

比之前功能（0 上游改动）多出 3 处 `custom_change`。

**缓解**：每处改动极小（1-5 行），标记清晰，上游同步时 diff 可控。

## 六、简化替代方案（0 上游改动）

如果不想改上游文件，有一个降级方案：

| 方案 | 做法 | 缺点 |
|---|---|---|
| **降级方案** | 用 `insertPromptText` 在输入框写入 `@filepath1\n@filepath2\n...` | `@` 文本不会被解析为附件引用，发送时仅作为纯文本 |
| **可行性** | 无需任何上游改动 | ❌ **不能实现 PRD 需求** — 文件不会被后端识别为引用 |

**结论：降级方案不满足 PRD 需求，必须走上游改动方案。**

## 七、成本收益总结

| 维度 | 评估 |
|---|---|
| **开发成本** | ~2 小时（2 个 Action + 3 处 custom_change + 目录扫描逻辑） |
| **上游维护成本** | 中（3 处标记，每次同步需检查） |
| **用户价值** | 高 — 批量添加文件上下文是高频需求 |
| **风险** | 中 — 新会话时序需测试验证 |

**建议**：可以实现。3 处 `custom_change` 每处仅 1-5 行，标记清晰可控。核心价值高，值得投入。
